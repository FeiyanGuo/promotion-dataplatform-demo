# 晋升数据中台 · 部署 Checklist

> 用途：从原型走向内网正式部署的落地清单。
> 每项落地后打勾；标注 ⚠️ 的是原型教训换来的必做项。

## 一、前置审批（先谈妥再动工）

- [ ] HR 负责人书面确认数据范围与 BP 可见口径（哪些数据、到哪一级组织）
- [ ] IT 安全评审通过：数据分级、存储位置、传输加密、审计要求
- [ ] 确认部署位置：**内网服务器或 HR 托管环境**，禁止公网暴露
- [ ] 确认接入公司 SSO（飞书/钉钉/AD），明确账号生命周期归属（跟 HR 系统走）

## 二、环境准备

- [ ] 服务器：Node.js 20+，内网域名 + HTTPS 证书
- [ ] 进程守护：PM2 / systemd / Windows 服务，**开机自启 + 崩溃自动拉起**
- [ ] ⚠️ **端口占用监控**：配置 strictPort（已内置），并监控端口只能有一个监听实例——原型阶段曾因多个残留实例各占 IPv4/IPv6 端口，导致请求落到不同版本的服务上，排查代价很高
- [ ] 日志：应用日志 + 审计日志分离落盘，审计日志**只追加、定期归档**（建议保留 ≥2 年）

## 三、数据初始化（首次上线）

- [ ] 收集全量历史晋升长表（各年合并），通过「追加补数」导入
- [ ] 收集最新花名册，确认含【中心】【部门】两列，通过「全量替换」导入
- [ ] 核对：架构图生成正确、各部门人数与人事系统一致
- [ ] 创建 BP 账号（接 SSO 后此步自动化），按组织架构页完成授权
- [ ] 用 1 个 BP 账号抽查：可见人数、晋升记录数与人事口径一致
- [ ] **首次授权前先「导出授权配置」留底**，存入受控目录

## 四、安全加固（上线前必须完成）

- [ ] SSO 替换明文密码，移除 users.json 中的 password 字段
- [ ] 会话持久化（Redis/DB），服务重启不踢人
- [ ] JSON 文件 → SQLite/数据库，写操作加事务（多管理员并发场景）
- [ ] 数据库/数据文件目录权限收紧（仅服务账号可读写）
- [ ] 下载文件加水印（行级暗记 + 下载人标识）
- [ ] 异常行为告警：短时间大量导出、非工作时间批量下载 → 通知 OD

## 五、上线验收用例（逐项过）

- [ ] BP 账号只能看到授权范围内数据；构造越权请求（改参数/改部门）被服务端收敛
- [ ] 中心授权 → 下挂部门数据自动可见；撤中心授权 → 子树权限即时收回
- [ ] 花名册替换后架构图自动更新，新部门进入授权列表
- [ ] 晋升数据重复导入不产生重复记录（主键去重）
- [ ] 坏文件导入被整体拒绝，现有数据不受影响（原子性）
- [ ] 查询/导出/授权变更均能在审计日志中查到（时间、人、条件、行数）
- [ ] 服务重启后会话策略符合预期（SSO 接入后应无感）

## 六、上线后运维节奏

- [ ] 每半年晋升数据发布后：追加补数导入 + 抽查核对
- [ ] 花名册月度/季度更新：全量替换 + 核对架构图
- [ ] BP 轮岗：当天在组织授权页调整（单人在页面改，批量调整用导出/导入）
- [ ] 每季度复核一次授权配置与审计日志（重点看"导出"类操作）
- [ ] 每年做一次权限盘点：离职/转岗账号是否已收回

## 七、回滚方案

- [ ] 数据回滚：导入前保留上一份 promotions/roster 导出，坏导入用「全量替换」回灌
- [ ] 授权回滚：每次批量导入授权配置前留底，回导即恢复
- [ ] 服务回滚：发布新版本前保留上一版 dist/ 与 server/，nginx/反向代理切流回退
